# Decision: 录制成品放在保存目录本层并按网页标题命名

Status: proposed

随 1.0.6 发布。

## Problem

1.0.5 及以前，每次录制都建一个 `capture-<uuid>` 子目录，成品 `capture-<N>.mkv` 和原始轨道 `track-*`、`capture.json`、`diagnostics.json`、`ffmpeg-stderr-*.txt` 放在一起。Windows 默认隐藏扩展名，用户分不清哪个文件才是视频（B 站评论反馈）。界面上的“复制路径”给的也是这个子目录里的文件路径。

## Proposal

- 合并流程不变，先在会话目录里生成 `capture-N.mkv`。
- 只有整次录制判定为 `complete` 时（所有分段都合并成功且没有错误），才把成品挪到会话目录的上一层，也就是用户的保存目录（`native-host/src/capture_export.rs`）：
  - 文件名用网页标题，按 `safe_file_stem` 清理掉不能用的字符；取不到标题时用 `capture-<id 前 8 位>`；
  - 有多个分段时加“ - 片段N”；
  - 遇到重名先用 `create_new` 占住名字，再替换进去，名字后面依次加 ` (1)`、` (2)`。这样既不会覆盖用户已有的文件，两个录制同时完成时也不会抢同一个名字；
  - 挪动失败时成品留在原处，`outputs` 指向原路径，诊断记录里写一条 `output-export`。
- 未完成（partial）或中断（interrupted）的成品留在子目录里，保证“重新生成文件”能直接覆盖。
- 原始轨道和记录文件始终留在子目录，不删除。
- 删除录制记录时，先删除挪出去的成品，再删子目录。要删除的成品必须同时满足：路径就在会话目录的上一层、扩展名是 `.mkv`、是普通文件而不是符号链接、没有被其他录制记录引用。文件不存在不算错误；删除失败时保留这条记录，方便重试。
- 界面上的“复制文件夹路径”复制成品所在的文件夹。“打开文件夹”通过本地助手的 `capture.reveal`（能力 `capture-reveal-v1`）打开资源管理器并选中文件，只接受该记录 `outputs` 里仍然存在的普通文件。

## Alternatives considered

- 合并成功后删掉原始轨道：目录最干净，但会失去“重新生成文件”和排查问题的依据。
- 只在界面上说明哪个文件是成品：用户在文件管理器里看到的仍然是一堆文件，问题没有解决。

## Risks

- 删除时依据的是 `capture.json` 里记录的 `outputs`。如果有人在本机改了这个文件，删除记录可能删掉保存目录本层的其他 `.mkv`。这需要本机有人主动篡改，风险低。收紧的办法是单独记录“由流萤挪出去的路径”，只删那一个，留待以后再做。
- 挪出去的成品和子目录分开放，用户手动移动或删除其中一个后，记录可能只指向一半。删除时找不到文件不报错；“打开文件夹”会提示找不到文件。
- 旧记录的成品仍在子目录里，删除逻辑对它们照常适用，不需要迁移。

## Verification

- `native-host/src/capture_export.rs` 和 `capture.rs` 的单元测试覆盖：按标题命名、重名加序号、多段命名、取不到标题时的回退名、挪动失败时留在原处、删除只删本层 `.mkv`、仍被其他记录引用时不删、`reveal` 只接受仍存在的成品。
- `tools/test-native-capture.mjs` 用真实 FFmpeg 合并：完成后成品位于 captures 目录本层。
- 2026-10-08 用户在 Chrome 中实测 B 站：成品以网页标题保存在保存目录，“打开文件夹”和“复制文件夹路径”都正常。
